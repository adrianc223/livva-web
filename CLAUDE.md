# CLAUDE.md

This file documents how `livva-web` works. **Living document** — update the relevant section here in the same session you ship a change, same convention as the main app.

**Onboarding a new machine**: `docs/ONBOARDING.md` covers what to install/authenticate so an AI assistant (or a new dev) can pick this repo back up on any machine — accounts, tools, one-time logins, and how this project relates to its sibling repo `Condo-Admin-Tool` (GitHub/Vercel locations for both, what's shared vs. independent).

## Project overview

`livva-web` is the public, informational landing page for **Livva** — a separate, much smaller Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 project from the real product (`Condo-Admin-Tool`, elsewhere on this machine). It's a single scrolling page (`src/app/page.tsx` → `src/components/landing/LandingPage.tsx`) pitching the product ("Uniendo comunidades"), presenting 3 pricing tiers by unit count, and capturing leads through a contact form. There is **no database, no auth, and no multi-tenancy** here — this is intentionally the lightest possible project, not a scaled-down clone of the main app's architecture.

Visual identity (palette, fonts, hero styling) is deliberately ported from the main app so the two feel like the same brand — see `src/app/globals.css` (pine palette + `mobile`/`tablet` breakpoints, copied from Condo-Admin-Tool's `globals.css`) and `src/components/landing/Hero.tsx` (dark pine hero panel with the same decorative ring, copied from `LoginScreen.tsx`'s style). `src/components/Logo.tsx` and `public/logo-light.svg`/`logo-dark.svg` are ported verbatim from the main app. `src/app/icon.png`/`apple-icon.png` are copied directly from the main app's already-generated brand icons (same 512×512 pine-square mark) rather than regenerated.

## Commands

```bash
npm run dev      # start Next.js dev server (localhost:3000 — falls back to the next free port if that's taken, e.g. by Condo-Admin-Tool's own dev server; check the terminal output for the real port)
npm run build    # next build
npm run start    # run production build
npm run lint     # eslint (flat config, eslint-config-next)
```

No database, no Prisma, no `.env` requirement to run the dev server. `RESEND_API_KEY`/`EMAIL_FROM`/`LEAD_NOTIFY_EMAIL` are only needed for the contact form to actually deliver an email (see "Lead capture" below) — without them the form still works from the visitor's side, it just soft-fails to send (console warning) rather than throwing.

## Page structure (`src/components/landing/`)

One page, composed in `LandingPage.tsx` (a client component, since it owns the shared lead-form state) in this order: `Header` (sticky nav) → `Hero` (`#inicio`) → `ValueProps` → `Features` (`#funciones`) → `MobileShowcase` → `HowItWorks` → `Security` (`#seguridad`) → `Pricing` (`#planes`) → `ContactSection` (`#contacto`) → `Footer`.

- **Real app screenshots, not mockups**: `Hero`, `Features`, and `MobileShowcase` all show actual captures of Condo-Admin-Tool's dashboard (`public/screenshots/*.png`), framed with `DeviceFrames.tsx`'s `BrowserFrame`/`PhoneFrame` (plain CSS chrome — a dot-bar top strip for desktop, a rounded bezel + notch for mobile; no image assets of their own). `object-cover object-top` deliberately crops toward the top of every screenshot, since every capture's bottom edge is the sidebar's account-switcher footer — irrelevant noise on a marketing page. **Regenerating these**: seed a disposable `isTest` condominium with realistic sample data (units, confirmed + pending payments, announcements, an approved + a pending reservation, a published vendor with products, a pending vendor, a resident↔admin conversation) via a throwaway `prisma/_check.ts`-style script in `Condo-Admin-Tool` — set `tutorialsEnabled: false`/`pwaTutorialEnabled: false` on every seeded `User` so the feature-tour/PWA-modal auto-start doesn't fight Playwright for clicks — then drive the real app with Playwright (log in with the real password form, screenshot each page at the desired viewport). **Capture against a production build** (`npm run build && npx next start -p 3010` in `Condo-Admin-Tool`, not `next dev`) — the dev-mode indicator badge otherwise shows up in every shot. Delete the seed script and the seeded condominium/users when done; never commit real screenshots that include another real condo's data.
- **Hero layout** (2026-09): below `tablet` (1000px) it's a single centered column with no screenshots at all — deliberately text-only on a phone-width viewport, matching how it already looked before screenshots existed. At `tablet:` and up it becomes a 2-column grid (copy + CTAs left, screenshots right) purely from DOM source order (text block first, image block second) — no `tablet:order-*` needed. The brand mark appears exactly once per breakpoint: a small centered one above the eyebrow below `tablet`, or a larger left-aligned one at `tablet:` — and `Header.tsx`'s own logo is `tablet:hidden` for exactly the same reason (it would otherwise be the second logo on a wide viewport, since the Hero's is already visible there). The right column stacks `BrowserFrame` (desktop capture, `h-[300px] w-full`, behind) and `PhoneFrame` (mobile capture, `h-[270px] w-[132px]`, absolutely positioned `-bottom-12 -right-6` so it overlaps the browser frame's bottom-right corner with its own shadow) — sized so the phone is the visually bigger, closer element despite representing the smaller screen.
- **Features carousel**: `Features.tsx`'s track is a real `overflow-x-auto` flex row (`FEATURES` duplicated once into `LOOP`, `globals.css`'s `.no-scrollbar` hides the native scrollbar visually only) driven by a `requestAnimationFrame` loop that increments `scrollLeft` and wraps it back by exactly half the scrollable width whenever it crosses that boundary — the wrap is imperceptible only because both halves render identical content, and it's re-checked every frame (not just while auto-scrolling) so a manual drag that lands past the boundary gets silently renormalized too. **Real scrolling, not a CSS transform**, specifically so it's actually interactive: `onPointerDown`/`onPointerMove` implement click-and-drag on `pointerType === "mouse"` only (touch/pen pointers fall through untouched to the browser's own native touch-scroll on the same element — reimplementing that by hand would only fight it), and two `ChevronLeft`/`ChevronRight` arrow buttons (`tablet:` and up only; touch already has swipe) call `scrollBy({behavior:"smooth"})`. Auto-scroll pauses on hover, during any drag, and briefly after a manual drag/arrow-click (`pauseThenResume`), and is skipped entirely under `prefers-reduced-motion` (manual interaction still works either way — only the *automatic* motion is what that preference disables). **Gotcha already hit**: the track needs real vertical padding (`py-8`) — setting `overflow-x-auto` forces `overflow-y` to also clip (there's no such thing as clipping one axis and not the other per the CSS spec once either is non-`visible`), which was silently cutting off each card's own `box-shadow` top/bottom before this padding was added.
- **Pricing** (`Pricing.tsx` + `PricingCard.tsx` + `PricingCalculator.tsx`) reads from `src/lib/pricing.ts`'s `PRICING_PLANS`/`resolvePlanForUnits`/`ANNUAL_DISCOUNT_PERCENT` — **these numbers are hand-kept in sync with Condo-Admin-Tool's `src/lib/billing/annualPricing.ts`** (updated 2026-09-09 to a graduated, tax-bracket-style scheme: ₡1,500/unit for the first 30 units, ₡1,400/unit for the next 90 up to 120, fully custom/negotiated past that — replacing an earlier flat ₡1,300/₡950/₡750-per-plan model; 12% annual discount unchanged), since this repo has no access to that app's `src/lib`. If the main app's tiers ever change, update `src/lib/pricing.ts` here by hand to match — see `resolveMonthlyTotalForUnits` there for the shared graduated-total logic both this file's `resolvePlanForUnits` and the main app's billing suggestion/self-serve-signup code build on independently.
- **Lead capture**: clicking a `PricingCard`'s "Iniciar demo" button now opens the `DemoWizard` (see "Self-serve demo onboarding" below) rather than jumping straight to the contact form — `selectPlanAndScroll` (from `src/components/landing/hooks/useLeadForm.ts`, owned by `LandingPage.tsx` and passed down as props) is still what the wizard's own "contact me instead" branches fall back to: it sets the shared `selectedPlan`/`unitCount` state and scrolls to `#contacto`, where `ContactSection` renders that plan (and unit count, if the wizard passed one along) pre-filled. This hooks-per-domain pattern (state/submit logic in its own `useX.ts`, not inlined into the section component) follows the same convention the main app uses for all its domain hooks.
- Submitting the form `POST`s to `/api/leads` (`src/app/api/leads/route.ts`), which validates every field server-side, checks a hidden honeypot field (`website`) for basic bot resistance, and calls `sendLeadNotificationEmail` (`src/lib/email/resend.ts`) — a near-verbatim port of the main app's `sendAdminFeedbackEmail` pattern (`Resend` client soft-fails if `RESEND_API_KEY` isn't set, `escapeHtml` on every interpolated field, styled HTML email matching the pine palette).
- **Footer** deliberately does **not** print a personal email address publicly — its "Contactanos" link just scrolls to `#contacto` instead. This site is public and indexable (see SEO below), so anything in it gets crawled/scraped; publishing a personal inbox on a page meant to be found by search engines invites spam in a way that wasn't the user's explicit call to make. If a business address is ever wanted here (e.g. `hola@livvaadmin.info`, since that domain is already verified in Resend — see "Lead capture" below), swap it in `Footer.tsx` directly. **"Términos y condiciones"/"Seguridad" links** (2026-09-10) open `LegalModal.tsx` — content ported verbatim from Condo-Admin-Tool's own `src/components/dashboard/LegalModal.tsx` (the modal the app itself already shows), not the shorter marketing-card summary already on this page in `Security.tsx` — that section stays as-is (a pitch, not the legal text) and the two now coexist without duplicating each other's role. `LandingPage.tsx` owns the `legalModal: "terms" | "security" | null` state (same shape as the main app's `page.tsx`) and renders `LegalModal` as a sibling of `DemoWizard`, same pattern.

## Lead capture — real, lands in the main app's dashboard

**This project still has no database of its own** — that hasn't changed. But since 2026-09-09, `POST /api/leads` does two things after validating the submission: (1) `sendLeadNotificationEmail` as before, and (2) a best-effort, **awaited** server-to-server `fetch` to `${CONDO_ADMIN_API_URL}/api/public/leads` (Condo-Admin-Tool, a separate Vercel project/database — see its own `CLAUDE.md`'s "Leads (from livva-web)" section for the receiving side) with an `Authorization: Bearer ${LANDING_LEADS_SECRET}` header. That call is wrapped in try/catch and never affects the response to the visitor — the email succeeding is still what `{ok:true}` actually promises; the DB-forward is a bonus. **It's `await`ed, not fire-and-forget** — a serverless function's execution can be frozen the instant its response is sent, so an un-awaited call here would frequently just never complete.

New env vars this needs (set in Vercel, never committed): `CONDO_ADMIN_API_URL` (`https://livva-admin.vercel.app`) and `LANDING_LEADS_SECRET` — **the exact same secret value** must also be set in Condo-Admin-Tool's own env vars, since it's what authenticates this call (there's no user session to present across a Vercel-project boundary). Without either var set, the route just logs a warning and skips the forward — the form still works, the lead just isn't persisted, same as before this existed.

From here, a lead shows up in `/master/leads` (a "Nueva" badge until opened) and in `/master/analytics`'s "Leads" tab (a 6-month trend chart + breakdown by requested plan) — both on the Condo-Admin-Tool side; nothing to maintain here beyond keeping the two env vars in sync if the secret is ever rotated.

`EMAIL_FROM` reuses the main app's already-DNS-verified Resend sending domain (`Livva <soporte@livvaadmin.info>`) rather than the shared `onboarding@resend.dev` sandbox address, since that domain is already proven to work in production for `Condo-Admin-Tool`. Both projects currently share one Resend account/domain — that's a deliberate reuse of existing, working infrastructure, not an accident.

## Self-serve demo onboarding

A visitor can go from "interested" to "logged into a real, working demo condominium" on Condo-Admin-Tool with nobody on either side lifting a finger (2026-09-09; full design/plan live in Condo-Admin-Tool's `docs/superpowers/specs/2026-09-09-self-serve-demo-onboarding-design.md`/`.../plans/2026-09-09-self-serve-demo-onboarding.md` — see that repo's own `CLAUDE.md` "Self-serve demo onboarding" section for the receiving side). `useDemoWizard.ts` + `DemoWizard.tsx` are a self-contained 2-step modal: **"choice"** (create a demo now vs. "prefiero que me contacten", the latter just calling the existing `selectPlanAndScroll` and closing — no separate logic) and **"solo-form"** (condominium name, admin name/email, unit count, plus its own honeypot field, same convention as `ContactSection`'s). A live price preview reuses `resolvePlanForUnits` — exactly `PricingCalculator`'s own visual pattern — and typing more than the self-serve ceiling swaps the submit button for "Contactar en su lugar" (calling `selectPlanAndScroll("metropoli", unitCount)` so the number carries over into the contact form instead of being lost). That ceiling is **not** a second hardcoded `120` — `exceedsSelfServe` is derived straight from `resolvePlanForUnits(...).monthlyTotal === null` (the same signal that already means "past the top tier, price is negotiated"), so there's exactly one place this boundary lives.

Submitting `POST`s to `` `${NEXT_PUBLIC_LIVVA_APP_URL}/api/public/demo-signup` `` — a new public env var (`NEXT_PUBLIC_LIVVA_APP_URL`, since nothing here previously pointed *at* Condo-Admin-Tool; `SITE_URL`/`APP_URL` in this repo refer to livva-web itself) needed because this is a genuine cross-origin browser call, unlike the server-to-server lead forward above. On success (`{ activationUrl }`) the wizard does `window.location.href = activationUrl`, leaving this site entirely and landing the new admin already logged into their demo. `condominium_exists`/`account_exists`/`unit_count_exceeds_self_serve` error codes each get their own message (`ERROR_MESSAGES` in `DemoWizard.tsx`); anything else falls back to a generic "no pudimos crear tu demo" retry message.

**"Do you manage several condominiums?" linking flow (2026-09-10)** — when `account_exists` comes back, `useDemoWizard.ts`'s `linkStep` state (`"prompt" | "password" | null`) drives a follow-up inside the same modal instead of just showing the plain error: a "¿Administrás varios condominios? Con tu mismo correo podés administrar varios condominios con tu cuenta desde la aplicación" prompt with Cancelar/Aceptar, then (on Aceptar) a password field. `startLinkPassword`/`cancelLink`/`submitLink` are separate functions from the plain `submit` — `submitLink` re-POSTs the exact same body plus `linkPassword`, and Condo-Admin-Tool's route only creates the new condominium (attaching it to the existing account) once that password verifies; see that repo's own CLAUDE.md "Linking a new demo to an existing account" for why a raw client-side "yes" click isn't enough proof on its own for a public, unauthenticated, cross-origin endpoint. `wizard.errorCode`'s plain `account_exists` message is suppressed (`!wizard.linkStep`) while this flow is showing, since the popup already covers it; Cancelar drops back to the plain form with that message still visible so the visitor can just edit the email instead.

**Monthly/annual choice (2026-09-10)**: the solo-form step also carries a `billingCycle` toggle (`MONTHLY`/`ANNUAL`, mirrors `PricingCalculator`'s own toggle below) sent in the `demo-signup` POST body — the live price preview switches between `resolvePlanForUnits`'s plain monthly total and `resolveAnnualPlanForUnits`'s discounted annual total (`pricing.ts`, new — mirrors Condo-Admin-Tool's `suggestAnnualAmount` exactly: same 12% discount, same round-to-nearest-₡1,000) so what's shown here always matches what the receiving app actually charges. **`PricingCalculator.tsx` has its own, separate Mensual/Anual toggle** — deliberately local state, affecting only that box's own displayed number; the 3 plan cards below it keep their static "-12% pagando anual" note regardless of this toggle's position, so there's no risk of the calculator's choice silently changing what a card appears to cost.

**Metrópoli skips the wizard entirely** — that plan has no self-serve rate (`monthlyRatePerUnit === null`, matching the demo wizard's own >120-unit ceiling), so its `PricingCard` button reads "Contáctanos" (branched on that same `null` check) and `LandingPage.tsx`'s `onSelectPlan` routes `"metropoli"` straight to `selectPlanAndScroll` instead of `wizard.open(planId)` — identical to what choosing "Prefiero que me contacten" from inside the wizard already did, just skipping the extra click.

**Entry points**: `Pricing.tsx`'s `onSelectPlan` prop is wired (from `LandingPage.tsx`) to `wizard.open(planId)` instead of `selectPlanAndScroll` directly — `Pricing.tsx` itself needed no code changes, since `onSelectPlan` was already a plain `(planId: string) => void` callback passed straight through (`LandingPage.tsx` branches `"metropoli"` to `selectPlanAndScroll` instead — see above). `Header.tsx` also grew a second CTA, "Iniciar demo" (`max-mobile:hidden` — a phone-width header only has room for one CTA, and every pricing card's own button already reaches the same wizard on mobile), calling `wizard.open()` with no pre-selected plan. **Restyled 2026-09-10**: this button is now the bold, filled, icon-carrying CTA (was the outline one) and "Contáctanos" (also fixed — was missing its accent, here and in `Footer.tsx`) stepped down to the plain outline secondary, since self-serve signup converts better for both sides than a manual contact request.

**Local cross-origin testing**: `NEXT_PUBLIC_LIVVA_APP_URL` in `.env.local` must point at whatever port Condo-Admin-Tool's dev server actually runs on, and that origin must be one of the exactly-two literal origins Condo-Admin-Tool's `demo-signup` route allows via CORS (`https://livvaadmin.com` and `http://localhost:3000`, no wildcard, no third dev-convenience origin — it's a real unauthenticated write endpoint) — which means **livva-web itself has to run on port 3000** for local end-to-end testing to work at all, so run Condo-Admin-Tool on a different port (`next dev -p 3001`) and, since that app's own `APP_URL` env var (used server-side to build the activation link, unrelated to `NEXT_PUBLIC_LIVVA_APP_URL` here) normally defaults to `http://localhost:3000` too, override it for that one dev process (`APP_URL="http://localhost:3001" npm run dev -- -p 3001`) rather than editing its committed `.env`.

## SEO & accessibility

**Unlike the main app** (Condo-Admin-Tool, whose product is almost entirely a private, login-gated dashboard where classic SEO barely applies), **this entire site is meant to be found and indexed** — it's the public pitch for the product, so real marketing-site SEO applies in full, not just "keep the private app out of Google."

- **Indexing**: `src/app/robots.ts` allows everything (`Allow: /`) and points at `src/app/sitemap.ts`, which lists the one real URL. Both read the deployed URL from `src/lib/siteUrl.ts` (`SITE_URL`) — **don't hardcode the domain in a third place**; that's exactly the bug this project already hit once (see below).
- **Metadata** (`src/app/layout.tsx`): a single `title`/`description`/`openGraph` block (there's only one route, so no per-page `generateMetadata` is needed). `<html lang="es">` is set correctly — all UI copy is Spanish.
- **Open Graph / Twitter card image**: `src/app/opengraph-image.png` (1200×630, dark-pine hero style matching the real hero section) is a **static file** using Next's file-based convention — Next auto-injects `og:image`/`twitter:image` (and infers `twitter:card: summary_large_image`) from its mere presence, no `metadata.openGraph.images` entry needed. Verified by actually inspecting the rendered `<head>` of a production build (`npm run build && npx next start`, then `curl | grep og:`), not just by reading the JSX — the same discipline the main app's own `seo` agent insists on, because Next's metadata merging can surprise you. **Regenerating it**: it was produced by a disposable route (`src/app/og/route.tsx` using `next/og`'s `ImageResponse`, 1200×630, plain inline styles since Satori doesn't support Tailwind/className) — start the dev server, `curl http://localhost:PORT/og -o src/app/opengraph-image.png`, then delete the route. Same disposable-route-then-static-file technique the main app used for `icon.png`/`apple-icon.png`.
- **A real bug already caught and fixed here**: `layout.tsx`, `robots.ts`, and `sitemap.ts` each originally hardcoded their own `process.env.APP_URL || "https://livva.vercel.app"` fallback — and that fallback string was simply wrong (the real domain is `livva-web.vercel.app`, one word longer). Because `APP_URL` *is* set correctly in Vercel's Production env, this never broke the live site — but it would have silently produced wrong `og:url`/sitemap URLs in any environment missing that var (local `npm run build`, a future Preview deploy). Fixed by centralizing the fallback into `src/lib/siteUrl.ts`'s single `SITE_URL` export, so there's exactly one string to get right. **Lesson for next time**: when the same fallback value needs to appear in more than one file, factor it out immediately rather than copy-pasting a literal — that's precisely how this drifted.
- **Accessibility (WCAG)** — checked directly against this codebase, not assumed:
  - Exactly one `<h1>` on the page (in `Hero.tsx`); every section below it uses `<h2>`, every card `<h3>` — verified with a grep sweep across `src/components/landing/`, not just visual skim.
  - Every `<img>` carries real `alt` text — the logo (`Logo.tsx`, `alt="Livva"`) and every app screenshot (`DeviceFrames.tsx`'s `BrowserFrame`/`PhoneFrame`, a per-image `alt` describing what's shown, e.g. "Resumen del condominio en Livva") — verified with a grep for `<img` lacking `alt=` (zero hits).
  - Every form field in `ContactSection.tsx` has a real `<label htmlFor>` / `<input id>` pair, not a placeholder-as-label.
  - Focus states: the only place a default outline is removed is the form inputs (`outline-0` in `ContactSection.tsx`), and it's always paired with a replacement (`focus:border-primary` + a soft box-shadow ring) — verified with a grep for `outline-none`/`outline: none` used *without* a paired focus treatment (zero hits). Links and buttons elsewhere keep the browser's default focus ring untouched.
  - Color contrast rides on the same pine tokens (`--text`/`--text-muted`/`--primary` against `--background`/`--surface`) already used throughout the main app — no new one-off colors were introduced.
- **Core Web Vitals**: no heavy client-side data fetching (no DB, one small `fetch` on form submit only). The app screenshots (`public/screenshots/*.png`) are plain `<img>` tags, not `next/image` — a deliberate choice matching `Logo.tsx`'s existing precedent (same ESLint `no-img-element` warning, accepted there already) rather than restructuring every `DeviceFrames` layout around `next/image`'s `fill`-plus-positioned-parent requirement; each file is small (well under 100KB) and there are under a dozen of them, so this is a real but minor tradeoff, not a real regression risk. If screenshots are ever added in bulk or the Hero's above-the-fold one becomes a measured LCP problem, that's the point to revisit `next/image`.
- **Structured data (JSON-LD)**: not added yet — genuinely low-value before the domain/pricing are finalized (see `docs/ROADMAP.md`). Worth adding (`Organization`/`Product`) once a real domain is bought.

The original landing copy predated self-serve demo signup and undersold it. `Hero.tsx` gained a one-line microcopy under its CTA ("Sin tarjeta, sin instalaciones — accedés al instante con solo un clic") instead of a second button, to respect the existing decision not to compete with the single "Iniciar demo" CTA there (see that file's own comment on why "Solicitar información" was dropped from the Hero). `DemoPromo.tsx`'s heading/subcopy and first point-card were reworded to lead with "empezás con un clic"/"empezá ahora mismo" framing. `HowItWorks.tsx` was the one section that actively contradicted the self-serve pitch — its 3 steps used to describe an admin-assisted setup ("Configuramos tu condominio...") left over from before self-serve existed, and it had no CTA at all; the steps now describe the real flow (fill the form → instant email activation → invite residents) and it gained the same `onOpenWizard` + "Iniciar demo" button every other pitch section already has.

## Maintenance mode and error pages

Same two mechanisms as Condo-Admin-Tool (2026-09-10) — see that repo's own CLAUDE.md for the full rationale, ported here identically:

- **Unplanned ("avería")**: `src/app/not-found.tsx`, `src/app/error.tsx`, `src/app/global-error.tsx` — branded replacements for Next's default fallbacks, styled with this site's own tokens (`bg-primary-soft`/`text-primary` for the icon chip, since this repo has no `--danger`/`--warning` tokens or `shadow-card` utility the way the main app does). `error.tsx`'s recovery prop is `retry()` (Next 16.3.0+), not the older `reset()`. `global-error.tsx` doesn't inherit `globals.css` — inline styles/hardcoded colors only.
- **Planned ("mantenimiento")**: `src/proxy.ts` rewrites every request to `src/app/mantenimiento/page.tsx` while `process.env.MAINTENANCE_MODE === "true"` — an env var, not a DB flag (this site has no database at all, so a toggle would mean a cross-origin call to Condo-Admin-Tool's API for no real benefit). Set/unset independently in this project's own Vercel env vars; no in-app switch. No `/master`-equivalent here to exempt — the whole site is gated.

## Conventions

- **UI text** is Spanish; **code comments** are English — same split as the main app.
- Tailwind CSS v4 utility classes only — this project has no legacy plain-CSS "hub classes" to preserve (unlike the main app's deliberate `.panel`/`.status`/etc. exception), so every element here should be 100% Tailwind.
- Color tokens live in `globals.css`'s `@theme inline` block (`--color-primary`, `--color-text-muted`, etc.) — reuse them, don't hardcode hex values.
- Only two real breakpoints: `mobile` (720px), `tablet` (1000px) — no `lg`/`xl`/`2xl`.
- No manual dark-mode toggle (v1) — dark tokens live under `@media (prefers-color-scheme: dark)`, and Tailwind's default `dark:` variant already follows that.
- `clsx` for conditional classNames; never combine an always-applied Tailwind utility with a conditionally-appended one for the same CSS property (see `PricingCard.tsx` for the correct mutually-exclusive-ternary pattern) — same gotcha the main app has documented.
- New interactive logic goes in its own hook under `src/components/landing/hooks/useX.ts`, not inlined into a section component.
- A single fallback/constant value needed by more than one file (a URL, a shared copy string) belongs in its own module (`src/lib/siteUrl.ts` is the precedent) — don't copy-paste a literal into a second file, see the SEO section above for what that already cost once.
- Path alias `@/*` → `src/*`.
- 5 subagents live under `.claude/agents/` (`frontend`, `backend`, `security`, `qa`, `seo`), ported from the main app and rescoped to what this single-page site actually needs.
- **Document as you go**: update this file's relevant section in the same session you change how a section, the lead flow, or a pattern works.
