# CLAUDE.md

This file documents how `livva-web` works. **Living document** — update the relevant section here in the same session you ship a change, same convention as the main app.

**Onboarding a new machine**: `docs/ONBOARDING.md` covers what to install/authenticate so an AI assistant (or a new dev) can pick this repo back up on any machine — accounts, tools, one-time logins, and how this project relates to its sibling repo `Condo-Admin-Tool` (GitHub/Vercel locations for both, what's shared vs. independent).

## Project overview

`livva-web` is the public, informational landing page for **Livva** — a separate, much smaller Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 project from the real product (`Condo-Admin-Tool`, elsewhere on this machine). Its homepage is a single scrolling page (`src/app/page.tsx` → `src/components/landing/LandingPage.tsx`), joined since 2026-09-10 by two bottom-of-funnel content pages (`/preguntas-frecuentes`, `/livva-vs-excel-whatsapp` — see "SEO & accessibility" below), so this is no longer a strictly one-page site pitching the product ("Uniendo comunidades"), presenting 3 pricing tiers by unit count, and capturing leads through a contact form. There is **no database, no auth, and no multi-tenancy** here — this is intentionally the lightest possible project, not a scaled-down clone of the main app's architecture.

Visual identity (palette, fonts, hero styling) is deliberately ported from the main app so the two feel like the same brand — see `src/app/globals.css` (pine palette + `mobile`/`tablet` breakpoints, copied from Condo-Admin-Tool's `globals.css`) and `src/components/landing/Hero.tsx` (dark pine hero panel with the same decorative ring, copied from `LoginScreen.tsx`'s style). `src/components/Logo.tsx` and `public/logo-light.svg`/`logo-dark.svg` are ported verbatim from the main app. `src/app/icon.png`/`apple-icon.png` are copied directly from the main app's already-generated brand icons (same 512×512 pine-square mark) rather than regenerated.

## Commands

```bash
npm run dev      # start Next.js dev server (localhost:3000 — falls back to the next free port if that's taken, e.g. by Condo-Admin-Tool's own dev server; check the terminal output for the real port)
npm run build    # next build
npm run start    # run production build
npm run lint     # eslint (flat config, eslint-config-next)
```

No database, no Prisma, no `.env` requirement to run the dev server. `RESEND_API_KEY`/`EMAIL_FROM`/`LEAD_NOTIFY_EMAIL` are only needed for the contact form to actually deliver an email (see "Lead capture" below) — without them the form still works from the visitor's side, it just soft-fails to send (console warning) rather than throwing.

## Page structure (`src/components/landing/`)

The **homepage** is composed in `LandingPage.tsx` (a client component, since it owns the shared lead-form state) in this order: `Header` (sticky nav) → `Hero` (`#inicio`) → `ValueProps` → `Features` (`#funciones`) → `MobileShowcase` → `HowItWorks` → `Security` (`#seguridad`) → `Pricing` (`#planes`) → `ContactSection` (`#contacto`) → `Footer`.

- **The other two pages** (2026-09-10) are thin `page.tsx` files that own only their own `metadata` block and delegate their body to one component each: `/preguntas-frecuentes` → `FaqPageContent.tsx` (rendering `src/lib/faqs.ts`'s `FAQS`, which also feeds the page's `FAQPage` JSON-LD) and `/livva-vs-excel-whatsapp` → `ComparisonPageContent.tsx`. Both wrap their body in `SiteChrome.tsx`, which supplies the same `Header`/`Footer` the homepage composes inline, plus the shared `DemoWizard`/`LegalModal` state and a `useDemoWizard` whose "contact me instead" fallback routes to `/#contacto` (the homepage's form) rather than scrolling in place — the homepage itself does **not** use `SiteChrome`, it renders `Header`/`Footer` directly from `LandingPage.tsx`. So adding a content page means writing its metadata + one content component wrapped in `SiteChrome`, not re-wiring navigation.
- **Real app screenshots, not mockups**: `Hero`, `Features`, and `MobileShowcase` all show actual captures of Condo-Admin-Tool's dashboard (`public/screenshots/*.png`), framed with `DeviceFrames.tsx`'s `BrowserFrame`/`PhoneFrame` (plain CSS chrome — a dot-bar top strip for desktop, a rounded bezel + notch for mobile; no image assets of their own). `object-cover object-top` deliberately crops toward the top of every screenshot, since every capture's bottom edge is the sidebar's account-switcher footer — irrelevant noise on a marketing page. **Regenerating these**: seed a disposable `isTest` condominium with realistic sample data (units, confirmed + pending payments, announcements, an approved + a pending reservation, a published vendor with products, a pending vendor, a resident↔admin conversation) via a throwaway `prisma/_check.ts`-style script in `Condo-Admin-Tool` — set `tutorialsEnabled: false`/`pwaTutorialEnabled: false` on every seeded `User` so the feature-tour/PWA-modal auto-start doesn't fight Playwright for clicks — then drive the real app with Playwright (log in with the real password form, screenshot each page at the desired viewport). **Capture against a production build** (`npm run build && npx next start -p 3010` in `Condo-Admin-Tool`, not `next dev`) — the dev-mode indicator badge otherwise shows up in every shot. Delete the seed script and the seeded condominium/users when done; never commit real screenshots that include another real condo's data.
- **Hero layout** (2026-09): below `tablet` (1000px) it's a single centered column with no screenshots at all — deliberately text-only on a phone-width viewport, matching how it already looked before screenshots existed. At `tablet:` and up it becomes a 2-column grid (copy + CTAs left, screenshots right) purely from DOM source order (text block first, image block second) — no `tablet:order-*` needed. The brand mark appears exactly once per breakpoint: a small centered one above the eyebrow below `tablet`, or a larger left-aligned one at `tablet:` — and `Header.tsx`'s own logo is `tablet:hidden` for exactly the same reason (it would otherwise be the second logo on a wide viewport, since the Hero's is already visible there). The right column stacks `BrowserFrame` (desktop capture, `h-[300px] w-full`, behind) and `PhoneFrame` (mobile capture, `h-[270px] w-[132px]`, absolutely positioned `-bottom-12 -right-6` so it overlaps the browser frame's bottom-right corner with its own shadow) — sized so the phone is the visually bigger, closer element despite representing the smaller screen.
- **Features carousel**: `Features.tsx`'s track is a real `overflow-x-auto` flex row (`FEATURES` duplicated once into `LOOP`, `globals.css`'s `.no-scrollbar` hides the native scrollbar visually only) driven by a `requestAnimationFrame` loop that increments `scrollLeft` and wraps it back by exactly half the scrollable width whenever it crosses that boundary — the wrap is imperceptible only because both halves render identical content, and it's re-checked every frame (not just while auto-scrolling) so a manual drag that lands past the boundary gets silently renormalized too. **Real scrolling, not a CSS transform**, specifically so it's actually interactive: `onPointerDown`/`onPointerMove` implement click-and-drag on `pointerType === "mouse"` only (touch/pen pointers fall through untouched to the browser's own native touch-scroll on the same element — reimplementing that by hand would only fight it), and two `ChevronLeft`/`ChevronRight` arrow buttons (`tablet:` and up only; touch already has swipe) call `scrollBy({behavior:"smooth"})`. Auto-scroll pauses on hover, during any drag, and briefly after a manual drag/arrow-click (`pauseThenResume`), and is skipped entirely under `prefers-reduced-motion` (manual interaction still works either way — only the *automatic* motion is what that preference disables). **Gotcha already hit**: the track needs real vertical padding (`py-8`) — setting `overflow-x-auto` forces `overflow-y` to also clip (there's no such thing as clipping one axis and not the other per the CSS spec once either is non-`visible`), which was silently cutting off each card's own `box-shadow` top/bottom before this padding was added.
- **The per-unit rates are derived from the published price** (2026-09-11): `monthlyRatePerUnit` is **₡1,504/₡1,416**, the taxable bases that produce a clean **₡1,700/₡1,600** once IVA is added. Round bases published ₡1,695/₡1,582. Never tidy them back — this repo has no test suite, so Condo-Admin-Tool's `annualPricing.test.ts` is the only guard, and these two files are hand-synced. The example totals stay ragged on purpose: graduating the published total instead was tried and rejected, because for 14 of the 120 reachable unit counts no integer base yields the round total (13% skips ₡10,200 at 6 units), which would advertise a figure the invoice misses by ₡1.
- **`Differentiation.tsx` answers "¿por qué esta y no otra?" and names nobody** (2026-09-11). A comparison table against the local competitors (KondoHome, Condova, iCondo) was researched and **deliberately rejected**: for the segment Livva actually serves — a junta directiva, not a management company shopping for software — those competitors are invisible, so publishing a table makes them visible at Livva's own expense. It would also have to quote their **unbundled entry tiers**, which undercut Livva's all-inclusive price by a lot (a base module at ₡678/unit; a flat $45/month regardless of size), and either list the four things Livva genuinely lacks — water-meter readings, aging reports, factura electrónica, native store apps — or mislead by omission. And a hand-maintained table of someone else's prices ages badly and silently in a repo with no test suite. The five claims that replaced it are true of Livva, verifiable, and do not expire when a competitor changes a price. **Placement is part of the argument**: immediately before `<Pricing />`, so it frames the number rather than competing with it.
- **`/livva-vs-excel-whatsapp` is the highest-value page on the site and was reachable only from the footer.** It is now in the header nav and teased at the end of `ValueProps`, where a reader who has just recognised their own spreadsheet is most likely to want it. It was also a day out of date — written 2026-09-10, the day before Documentos, Asamblea, Mantenimiento and Visitantes shipped, which are exactly the modules a spreadsheet **cannot** do; its original five points are all cases where Excel and WhatsApp *almost* work, the weakest ground to argue on. Five were added, of which **"cambio de junta directiva" is the strongest and was nowhere on the site**: it is the main reason a Costa Rican condominium loses its own administrative memory, and the exact moment somebody goes looking for a tool.
- **The factura-electrónica question is a FAQ, never a claim.** The predominant professional reading is that a condominium collecting only cuotas need not issue one — but the sources do not cite the instrument creating that exemption, they predate TRIBU-CR, and Hacienda did not respond when asked. Asserting it would be tax advice this site cannot stand behind, and a competitor page asserting the opposite is not grounds to assert this. The answer also has to keep two relationships apart: the condominium's own obligation, and the fact that **Livva always invoices the condominium**, since Livva is a contribuyente selling a taxable service. Blurring them leads a board to conclude Livva cannot invoice *them*.
- **IVA: every published price leads with the with-IVA total and carries the base as its second line** (2026-09-11, reversing the first pass, which led with the base and appended "+ IVA 13%"). **The deciding question is who the buyer is.** The "+ IVA" convention exists because a business buyer *credits* the IVA back, so the base is their real cost. Livva's buyer is a condominium board paying out of condominium funds, which almost certainly cannot credit it, so the total is the honest price and "+ IVA" would just make the first invoice bigger than the advertised number. **Pending confirmation from the accountant** — if a condominium can credit it, swap the two lines back; only which is the headline changes. `ivaBreakdown(base)` in `src/lib/pricing.ts` builds that second line in one place for all four surfaces (the three pricing components plus `DemoWizard`), mirroring the function of the same name in Condo-Admin-Tool's `src/lib/billing/iva.ts`. `PRICES_INCLUDE_IVA` is a separate decision — it says what the *stored* number means, and flipping it to make a display read better would cut revenue by 11.5%.
- **`layout.tsx`'s JSON-LD `AggregateOffer` derives `lowPrice`/`highPrice` through `totalWithIva`**, because the pricing cards show the with-IVA rate. Structured data that disagrees with the visible page is a spam signal, not a rounding difference. It is derived rather than hardcoded so the two cannot drift the next time a tier moves. **`PRICING_PLANS[].rateExplainer` is prose and is not derived** — it names "₡1 695" as a literal, so it has to be edited by hand whenever a rate or the IVA treatment changes; it was left saying ₡1 500 in the first pass and contradicted the headline on its own card.
- **Pricing** (`Pricing.tsx` + `PricingCard.tsx` + `PricingCalculator.tsx`) reads from `src/lib/pricing.ts`'s `PRICING_PLANS`/`resolvePlanForUnits`/`ANNUAL_DISCOUNT_PERCENT` — **these numbers are hand-kept in sync with Condo-Admin-Tool's `src/lib/billing/annualPricing.ts`** (updated 2026-09-09 to a graduated, tax-bracket-style scheme: ₡1,500/unit for the first 30 units, ₡1,400/unit for the next 90 up to 120, fully custom/negotiated past that — replacing an earlier flat ₡1,300/₡950/₡750-per-plan model; 12% annual discount unchanged), since this repo has no access to that app's `src/lib`. If the main app's tiers ever change, update `src/lib/pricing.ts` here by hand to match — see `resolveMonthlyTotalForUnits` there for the shared graduated-total logic both this file's `resolvePlanForUnits` and the main app's billing suggestion/self-serve-signup code build on independently.
  - **What a card says, and why it stopped being a feature checklist (2026-09-11)**: each card used to close with the same five-item ticked list — identical text in all three columns. That is the shape readers know from tiered SaaS pricing, where the list exists to show what a cheaper tier *withholds*, so printing an identical one three times sent people hunting for a difference that does not exist, and spent the card's best space saying nothing. **Nothing is gated by plan here and nothing is planned to be** — the tier only tracks unit count. So the shared list moved out of the cards into one band under the grid (`INCLUDED_EVERYWHERE` in `Pricing.tsx`), where "todas las funciones, en todos los planes" reads as the argument it always was and has room to name the real product instead of an abbreviated five.
  - Each card now spends that space on the two things only true of itself, both driven by new `PricingPlan` fields: `rateExplainer` (one sentence on what this tier's rate actually applies to) and `exampleUnits` (a representative count the card turns into a worked monthly total). **The worked total is computed through `resolvePlanForUnits`, never written down** — an example that can drift from the calculator sitting directly above it is worse than no example.
  - The explainer exists because the graduated model is the single most misread thing on this page: Comunidad's headline `₡1 400 / unidad / mes` invites a reader to multiply it by their unit count, and that is **not** what they would be charged, because their first 30 units stay at Esencial's ₡1 500. A 45-unit condominium pays ₡66 000, not ₡63 000. Better said on the card than discovered at signup.
  - The example hides itself on a card the calculator has matched (`!matched`), where the headline is already the reader's own real total and a second, larger figure for someone else's building is the one thing that could muddy it. The explainer stays — at that moment it is what explains their number. Metrópoli is never matched (no rate past 120), so its `Desde · 120 unidades` figure always shows; it is the top of the tier below, a real floor rather than an invented number.
- **Lead capture**: clicking a `PricingCard`'s "Iniciar demo" button now opens the `DemoWizard` (see "Self-serve demo onboarding" below) rather than jumping straight to the contact form — `selectPlanAndScroll` (from `src/components/landing/hooks/useLeadForm.ts`, owned by `LandingPage.tsx` and passed down as props) is still what the wizard's own "contact me instead" branches fall back to: it sets the shared `selectedPlan`/`unitCount` state and scrolls to `#contacto`, where `ContactSection` renders that plan (and unit count, if the wizard passed one along) pre-filled. This hooks-per-domain pattern (state/submit logic in its own `useX.ts`, not inlined into the section component) follows the same convention the main app uses for all its domain hooks.
- Submitting the form `POST`s to `/api/leads` (`src/app/api/leads/route.ts`), which validates every field server-side, checks a hidden honeypot field (`website`) for basic bot resistance, and calls `sendLeadNotificationEmail` (`src/lib/email/resend.ts`) — a near-verbatim port of the main app's `sendAdminFeedbackEmail` pattern (`Resend` client soft-fails if `RESEND_API_KEY` isn't set, `escapeHtml` on every interpolated field, styled HTML email matching the pine palette).
- **Footer** deliberately does **not** print a personal email address publicly — its "Contactanos" link just scrolls to `#contacto` instead. This site is public and indexable (see SEO below), so anything in it gets crawled/scraped; publishing a personal inbox on a page meant to be found by search engines invites spam in a way that wasn't the user's explicit call to make. If a business address is ever wanted here (e.g. `hola@livvaadmin.info`, since that domain is already verified in Resend — see "Lead capture" below), swap it in `Footer.tsx` directly. **"Términos y condiciones"/"Seguridad" links** (2026-09-10) open `LegalModal.tsx` — content ported verbatim from Condo-Admin-Tool's own `src/components/dashboard/LegalModal.tsx` (the modal the app itself already shows), not the shorter marketing-card summary already on this page in `Security.tsx` — that section stays as-is (a pitch, not the legal text) and the two now coexist without duplicating each other's role. `LandingPage.tsx` owns the `legalModal: "terms" | "security" | null` state (same shape as the main app's `page.tsx`) and renders `LegalModal` as a sibling of `DemoWizard`, same pattern.

## Lead capture — real, lands in the main app's dashboard

**This project still has no database of its own** — that hasn't changed. But since 2026-09-09, `POST /api/leads` does two things after validating the submission: (1) `sendLeadNotificationEmail` as before, and (2) a best-effort, **awaited** server-to-server `fetch` to `${CONDO_ADMIN_API_URL}/api/public/leads` (Condo-Admin-Tool, a separate Vercel project/database — see its own `CLAUDE.md`'s "Leads (from livva-web)" section for the receiving side) with an `Authorization: Bearer ${LANDING_LEADS_SECRET}` header. That call is wrapped in try/catch and never affects the response to the visitor — the email succeeding is still what `{ok:true}` actually promises; the DB-forward is a bonus. **It's `await`ed, not fire-and-forget** — a serverless function's execution can be frozen the instant its response is sent, so an un-awaited call here would frequently just never complete.

New env vars this needs (set in Vercel, never committed): `CONDO_ADMIN_API_URL` (`https://livva-admin.vercel.app`) and `LANDING_LEADS_SECRET` — **the exact same secret value** must also be set in Condo-Admin-Tool's own env vars, since it's what authenticates this call (there's no user session to present across a Vercel-project boundary). Without either var set, the route just logs a warning and skips the forward — the form still works, the lead just isn't persisted, same as before this existed.

From here, a lead shows up in `/master/leads` (a "Nueva" badge until opened) and in `/master/analytics`'s "Leads" tab (a 6-month trend chart + breakdown by requested plan) — both on the Condo-Admin-Tool side; nothing to maintain here beyond keeping the two env vars in sync if the secret is ever rotated.

`EMAIL_FROM` reuses the main app's already-DNS-verified Resend sending domain (`Livva <soporte@livvaadmin.info>`) rather than the shared `onboarding@resend.dev` sandbox address, since that domain is already proven to work in production for `Condo-Admin-Tool`. Both projects currently share one Resend account/domain — that's a deliberate reuse of existing, working infrastructure, not an accident.

## Self-serve demo onboarding

A visitor can go from "interested" to "logged into a real, working demo condominium" on Condo-Admin-Tool with nobody on either side lifting a finger (2026-09-09; full design/plan live in Condo-Admin-Tool's `docs/superpowers/specs/2026-09-09-self-serve-demo-onboarding-design.md`/`.../plans/2026-09-09-self-serve-demo-onboarding.md` — see that repo's own `CLAUDE.md` "Self-serve demo onboarding" section for the receiving side). `useDemoWizard.ts` + `DemoWizard.tsx` are a self-contained 2-step modal: **"choice"** (create a demo now vs. "prefiero que me contacten", the latter just calling the existing `selectPlanAndScroll` and closing — no separate logic) and **"solo-form"** (condominium name, admin name/email, unit count, plus its own honeypot field, same convention as `ContactSection`'s). A live price preview reuses `resolvePlanForUnits` — exactly `PricingCalculator`'s own visual pattern — and typing more than the self-serve ceiling swaps the submit button for "Contactar en su lugar" (calling `selectPlanAndScroll("metropoli", unitCount)` so the number carries over into the contact form instead of being lost). That ceiling is **not** a second hardcoded `120` — `exceedsSelfServe` is derived straight from `resolvePlanForUnits(...).monthlyTotal === null` (the same signal that already means "past the top tier, price is negotiated"), so there's exactly one place this boundary lives.

Submitting `POST`s to `` `${NEXT_PUBLIC_LIVVA_APP_URL}/api/public/demo-signup` `` — a new public env var (`NEXT_PUBLIC_LIVVA_APP_URL`, since nothing here previously pointed *at* Condo-Admin-Tool; `SITE_URL`/`APP_URL` in this repo refer to livva-web itself) needed because this is a genuine cross-origin browser call, unlike the server-to-server lead forward above. On success (`{ activationUrl }`) the wizard does `window.location.href = activationUrl`, leaving this site entirely and landing the new admin already logged into their demo. `condominium_exists`/`account_exists`/`unit_count_exceeds_self_serve` error codes each get their own message (`ERROR_MESSAGES` in `DemoWizard.tsx`); anything else falls back to a generic "no pudimos crear tu demo" retry message.

**"Do you manage several condominiums?" linking flow (2026-09-10)** — when `account_exists` comes back, `useDemoWizard.ts`'s `linkStep` state (`"prompt" | "password" | null`) drives a follow-up inside the same modal instead of just showing the plain error: a "¿Administrás varios condominios? Con tu mismo correo podés administrar varios condominios con tu cuenta desde la aplicación" prompt with Cancelar/Aceptar, then (on Aceptar) a password field. `startLinkPassword`/`cancelLink`/`submitLink` are separate functions from the plain `submit` — `submitLink` re-POSTs the exact same body plus `linkPassword`, and Condo-Admin-Tool's route only creates the new condominium (attaching it to the existing account) once that password verifies; see that repo's own CLAUDE.md "Linking a new demo to an existing account" for why a raw client-side "yes" click isn't enough proof on its own for a public, unauthenticated, cross-origin endpoint. `wizard.errorCode`'s plain `account_exists` message is suppressed (`!wizard.linkStep`) while this flow is showing, since the popup already covers it; Cancelar drops back to the plain form with that message still visible so the visitor can just edit the email instead.

**Monthly/annual choice (2026-09-10)**: the solo-form step also carries a `billingCycle` toggle (`MONTHLY`/`ANNUAL`, mirrors `PricingCalculator`'s own toggle below) sent in the `demo-signup` POST body — the live price preview switches between `resolvePlanForUnits`'s plain monthly total and `resolveAnnualPlanForUnits`'s discounted annual total (`pricing.ts`, new — mirrors Condo-Admin-Tool's `suggestAnnualAmount` exactly: same 12% discount, same round-to-nearest-₡1,000) so what's shown here always matches what the receiving app actually charges. **`PricingCalculator.tsx` has its own, separate Mensual/Anual toggle** — deliberately local state, affecting only that box's own displayed number; the 3 plan cards below it keep their static "-12% pagando anual" note regardless of this toggle's position, so there's no risk of the calculator's choice silently changing what a card appears to cost.

**Metrópoli skips the wizard entirely** — that plan has no self-serve rate (`monthlyRatePerUnit === null`, matching the demo wizard's own >120-unit ceiling), so its `PricingCard` button reads "Contáctanos" (branched on that same `null` check) and `LandingPage.tsx`'s `onSelectPlan` routes `"metropoli"` straight to `selectPlanAndScroll` instead of `wizard.open(planId)` — identical to what choosing "Prefiero que me contacten" from inside the wizard already did, just skipping the extra click.

**Entry points**: `Pricing.tsx`'s `onSelectPlan` prop is wired (from `LandingPage.tsx`) to `wizard.open(planId)` instead of `selectPlanAndScroll` directly — `Pricing.tsx` itself needed no code changes, since `onSelectPlan` was already a plain `(planId: string) => void` callback passed straight through (`LandingPage.tsx` branches `"metropoli"` to `selectPlanAndScroll` instead — see above). `Header.tsx` also grew a second CTA, "Iniciar demo" (`max-mobile:hidden` — a phone-width header only has room for one CTA, and every pricing card's own button already reaches the same wizard on mobile), calling `wizard.open()` with no pre-selected plan. **Restyled 2026-09-10**: this button is now the bold, filled, icon-carrying CTA (was the outline one) and "Contáctanos" (also fixed — was missing its accent, here and in `Footer.tsx`) stepped down to the plain outline secondary, since self-serve signup converts better for both sides than a manual contact request.

**Local cross-origin testing**: `NEXT_PUBLIC_LIVVA_APP_URL` in `.env.local` must point at whatever port Condo-Admin-Tool's dev server actually runs on, and that origin must be one of the exactly-two literal origins Condo-Admin-Tool's `demo-signup` route allows via CORS (`https://livvaadmin.com` and `http://localhost:3000`, no wildcard, no third dev-convenience origin — it's a real unauthenticated write endpoint) — which means **livva-web itself has to run on port 3000** for local end-to-end testing to work at all, so run Condo-Admin-Tool on a different port (`next dev -p 3001`) and, since that app's own `APP_URL` env var (used server-side to build the activation link, unrelated to `NEXT_PUBLIC_LIVVA_APP_URL` here) normally defaults to `http://localhost:3000` too, override it for that one dev process (`APP_URL="http://localhost:3001" npm run dev -- -p 3001`) rather than editing its committed `.env`.

## Precios: qué se redondea y qué no (2026-09-11)

**El redondeo al ₡100 de la base cobrada es un requisito tributario, no estética.** Las tarifas ₡1 504 / ₡1 416 se eligieron para que el precio *por unidad* publicado diera ₡1 700 / ₡1 600 redondos; eso rompió el *total*, porque el 13% de una base graduada no da colón entero en 115 de los 120 conteos alcanzables. El generador de facturas de la app declaraba `Tarifa 13.00` con un `ImpuestoNeto` que no era 13% del `SubTotal`. `resolvePlanForUnits` aplica el mismo redondeo que `resolveMonthlyTotalForUnits` en Condo-Admin-Tool — **una cotización previsualizada acá tiene que ser exactamente lo que cobra el signup**.

**Un total redondo con 13% exacto es imposible.** `base = 100·total/113` y 113 es primo, así que solo existe cuando 113 divide al total; ni ₡30 600 ni ₡99 000 lo son. Por eso el reparto es: **el cobro es exacto, la vista se redondea**.

- **El ejemplo de la tarjeta se redondea al ₡100 y dice "unos"** (≤₡12 de diferencia). Nadie tiene exactamente 18 unidades: un ejemplo es ilustrativo por definición, y cinco dígitos significativos ahí solo cuestan legibilidad. Da ₡30 600 y ₡99 000, que son bloques que el cerebro sostiene enteros.
- **La calculadora se queda exacta.** Ahí el visitante escribió su propio número, y la precisión es la prueba de que el precio es mecánico y no negociado por cliente. Es el único lugar donde la exactitud juega a favor.
- **La fila del ejemplo dejó de pesar más que el titular.** Estaba en `font-black` dentro de una caja rellena, justo encima del CTA — o sea, el número menos legible de la tarjeta ocupaba su mejor posición. Una sola cifra en negrita por tarjeta, y es la redonda.
- **Metrópoli ya no publica un total exacto de 6 dígitos.** Una cifra precisa bajo un encabezado "Personalizado" se lee como un ancla a la que te van a amarrar, y contradice el propio texto de la tarjeta ("es el punto de partida, no el techo"). Ancla en la tarifa desde la que arranca el tramo.
- `ANNUAL_DISCOUNT_PERCENT` es **17** (era 12). Se sincroniza a mano con `annualPricing.ts` de la app.

**La insignia del plan destacado decía "Rango más común entre nuestros clientes" y no había ni un cliente** — 0 pagos de plataforma confirmados, 0 condominios activos que no fueran de prueba. Era prueba social falsa en la tarjeta que más quiere que la elijan. Dice "El tamaño más común en Costa Rica", que es cierto y hace el mismo trabajo. **Cualquier afirmación de tracción en esta página tiene que verificarse contra la base antes de publicarse.**

**El carrusel de planes escondía el plan recomendado.** Medido a 375 y a 820: Esencial 100% visible, Comunidad **23%**, Metrópoli **0%**, sin puntos, flechas ni contador — o sea, en un condominio típico el visitante de celular veía completo solo el plan que no le corresponde. Un carrusel sin afordancia de paginación es contenido escondido. Ahora: una línea "Deslizá para ver los tres planes →" debajo de `tablet`, y las tarjetas pasan a `48%` en la banda 720–1000, donde una tarjeta de 640px dentro de un viewport de 820 desperdiciaba la mitad del ancho. Medido después: a 820 quedan **100 / 100 / 5%**.

## SEO & accessibility

**Unlike the main app** (Condo-Admin-Tool, whose product is almost entirely a private, login-gated dashboard where classic SEO barely applies), **this entire site is meant to be found and indexed** — it's the public pitch for the product, so real marketing-site SEO applies in full, not just "keep the private app out of Google."

- **Indexing**: `src/app/robots.ts` allows everything (`Allow: /`) and points at `src/app/sitemap.ts`, which lists the one real URL. Both read the deployed URL from `src/lib/siteUrl.ts` (`SITE_URL`) — **don't hardcode the domain in a third place**; that's exactly the bug this project already hit once (see below).
- **Metadata**: `src/app/layout.tsx` carries the sitewide `title`/`description`/`openGraph`/`alternates.canonical` block. Since the two content pages below (2026-09-10) exist, this is no longer the *only* metadata on the site — each of their own `page.tsx` exports its own `metadata` (real per-page `title`/`description`/canonical), the correct App Router pattern for a page-specific SEO target rather than everything sharing one block. `<html lang="es">` is set correctly — all UI copy is Spanish.
- **Real keyword/GEO gap found and fixed (2026-09-10 SEO/GEO audit, user-approved copy)**: the title (`"Livva — Uniendo comunidades"`), meta description, `<h1>` (`Hero.tsx`), and every section `<h2>` contained **zero** of the actual keywords a Costa Rican condo administrator searches — "condominio," "administración," "Costa Rica" appeared nowhere; the site said "residencial"/"comunidad" throughout instead. Confirmed via a live audit against 3 real competitor sites (ADICON, Macondo, ADMINSA) counting real term frequency — "condominio" appeared 17–201 times on their sites, "residencial" essentially never. Rewrote `layout.tsx`'s `TITLE`/`DESCRIPTION`, `Hero.tsx`'s h1/eyebrow/subcopy, and the h2 in `ValueProps.tsx`/`Pricing.tsx`/`HowItWorks.tsx`/`ContactSection.tsx` to lead with the real keyword while keeping the "uniendo comunidades" mission language as the framing/closing beat rather than the whole sentence (the user's explicit ask: keywords first-priority, but the site's overall voice still has to read as "we exist to unite communities," not a bare feature list). The `<title>` tag itself stays purely functional/keyword-only — titles aren't where brand voice earns its keep, that's what ranks.
- **Two new content pages (2026-09-10)**: `/preguntas-frecuentes` and `/livva-vs-excel-whatsapp` — the site's first pages beyond the single homepage, closing the "zero bottom-of-funnel content" gap the audit flagged as the highest-leverage content opportunity (BOFU/comparison content converts best for B2B SaaS and is exactly the shape an AI assistant answering "which tool should I use" wants to cite). Both linked from `Footer.tsx` (present on every page, so always crawlable regardless of entry point) and follow the same Server Component `page.tsx` (real metadata) + `"use client"` content component split as the rest of the site. `src/lib/faqs.ts` is the FAQ content's single source of truth — both the visible `FaqPageContent.tsx` and the `FAQPage` JSON-LD in `preguntas-frecuentes/page.tsx` import from it, so the schema can never claim a Q&A the page doesn't actually show.
- **`SiteChrome.tsx`** (`src/components/landing/`) — shared Header/Footer/DemoWizard/LegalModal wiring for these new subpages, extracted since `LandingPage.tsx` already had this exact wiring and a third near-identical copy crossed into "worth extracting" territory. `LandingPage.tsx` itself is deliberately left unrefactored (not migrated to also use `SiteChrome`) to avoid any risk of regressing the homepage for a pure duplication cleanup. Takes a render-prop `children` so page content can call `wizard.open()` for its own in-body CTA too, not just the shared header's. Its "prefiero que me contacten" fallback uses `useRouter().push("/#contacto")` (a real client-side navigation to the homepage's contact section) instead of `LandingPage.tsx`'s own in-page `scrollIntoView`, since a subpage has no `#contacto` element of its own to scroll to.
- **`Header.tsx`/`Footer.tsx` anchor links are now absolute-path** (`/#funciones`, not bare `#funciones`) and use Next's `<Link>`, not a plain `<a>` — a bare hash only scrolls within the *current* page, so from a subpage with no matching element it silently did nothing; `/#funciones` navigates home first when needed (a `<Link>` rather than `<a>` was required here too, since ESLint's `no-html-link-for-pages` rule flags a plain `<a>` pointing at an internal route). Same behavior as before when already on `/` — verified via Playwright (clicked a nav link from `/preguntas-frecuentes`, landed back on `/#funciones` correctly).
- **Open Graph / Twitter card image**: `src/app/opengraph-image.png` (1200×630, dark-pine hero style matching the real hero section) is a **static file** using Next's file-based convention — Next auto-injects `og:image`/`twitter:image` (and infers `twitter:card: summary_large_image`) from its mere presence, no `metadata.openGraph.images` entry needed. Verified by actually inspecting the rendered `<head>` of a production build (`npm run build && npx next start`, then `curl | grep og:`), not just by reading the JSX — the same discipline the main app's own `seo` agent insists on, because Next's metadata merging can surprise you. **Regenerating it**: it was produced by a disposable route (`src/app/og/route.tsx` using `next/og`'s `ImageResponse`, 1200×630, plain inline styles since Satori doesn't support Tailwind/className) — start the dev server, `curl http://localhost:PORT/og -o src/app/opengraph-image.png`, then delete the route. Same disposable-route-then-static-file technique the main app used for `icon.png`/`apple-icon.png`.
- **A real bug already caught and fixed here**: `layout.tsx`, `robots.ts`, and `sitemap.ts` each originally hardcoded their own `process.env.APP_URL || "https://livva.vercel.app"` fallback — and that fallback string was simply wrong (the real domain is `livva-web.vercel.app`, one word longer). Fixed by centralizing the fallback into `src/lib/siteUrl.ts`'s single `SITE_URL` export, so there's exactly one string to get right. **Lesson for next time**: when the same fallback value needs to appear in more than one file, factor it out immediately rather than copy-pasting a literal — that's precisely how this drifted.
- **The same drift bit this project a second time, now fixed end-to-end (found and resolved 2026-09-10, live SEO/GEO audit against the production site)**: `SITE_URL`'s own fallback still said `https://livva-web.vercel.app` — stale since `livvaadmin.com` went live 2026-09-09 — and Vercel's Production `APP_URL` env var was **never actually updated** to the new domain, so `og:url`, `sitemap.xml`, and `robots.txt`'s `Sitemap:` line were all still serving the old `*.vercel.app` domain in production, a real duplicate-content/crawler-confusion issue on the live site, not a hypothetical. `siteUrl.ts`'s fallback is now `https://livvaadmin.com` (defense-in-depth, so a missing env var degrades to the *correct* domain from now on), and the real Production `APP_URL` env var in Vercel is now also correctly set to `https://livvaadmin.com` and redeployed — **verified live**: `curl`ing production `sitemap.xml`/`robots.txt` after the fix both correctly return `livvaadmin.com` URLs. (En route to fixing this, the value was briefly set on the *wrong* Vercel project — `livva-admin`, not `livva-web` — which broke real activation-email links in the actual app for a short window; see Condo-Admin-Tool's `docs/ONBOARDING.md` for that incident, unrelated to this repo's own code.) Also added a real `<link rel="canonical">` (`metadata.alternates.canonical` in `layout.tsx`, and per-page in the two new pages below) — there was none before, a real gap while two live domains resolve to the same content in parallel.
- **Accessibility (WCAG)** — checked directly against this codebase, not assumed:
  - Exactly one `<h1>` on the page (in `Hero.tsx`); every section below it uses `<h2>`, every card `<h3>` — verified with a grep sweep across `src/components/landing/`, not just visual skim.
  - Every `<img>` carries real `alt` text — the logo (`Logo.tsx`, `alt="Livva"`) and every app screenshot (`DeviceFrames.tsx`'s `BrowserFrame`/`PhoneFrame`, a per-image `alt` describing what's shown, e.g. "Resumen del condominio en Livva") — verified with a grep for `<img` lacking `alt=` (zero hits).
  - Every form field in `ContactSection.tsx` has a real `<label htmlFor>` / `<input id>` pair, not a placeholder-as-label.
  - Focus states: the only place a default outline is removed is the form inputs (`outline-0` in `ContactSection.tsx`), and it's always paired with a replacement (`focus:border-primary` + a soft box-shadow ring) — verified with a grep for `outline-none`/`outline: none` used *without* a paired focus treatment (zero hits). Links and buttons elsewhere keep the browser's default focus ring untouched.
  - Color contrast rides on the same pine tokens (`--text`/`--text-muted`/`--primary` against `--background`/`--surface`) already used throughout the main app — no new one-off colors were introduced.
  - **Real WCAG AA contrast failure found, not yet fixed (2026-09-10, live Lighthouse audit)**: `text-text-muted` at small sizes (e.g. `Features.tsx`'s screenshot-caption line) measures 4.03:1 against the required 4.5:1 minimum — the `--color-text-muted` token itself (`#6c7869` on `#eef0e9`) is the likely root cause, which would affect every small-text usage of that token sitewide, not just this one instance. Flagged for `frontend`/`ui-ux` as a token-level decision, not fixed in the audit pass itself.
  - Each of the two new pages (below) still keeps exactly one `<h1>` — verified live, not just by reading the JSX.
- **Core Web Vitals**: no heavy client-side data fetching (no DB, one small `fetch` on form submit only). The app screenshots (`public/screenshots/*.png`) are plain `<img>` tags, not `next/image` — a deliberate choice matching `Logo.tsx`'s existing precedent (same ESLint `no-img-element` warning, accepted there already) rather than restructuring every `DeviceFrames` layout around `next/image`'s `fill`-plus-positioned-parent requirement. **This tradeoff's own stated reconsideration point was hit (2026-09-10, live Lighthouse audit against production)**: LCP measured 3.6s (mobile, lab data) against the 2.5s target, and the `Features.tsx` carousel wastes ~414KB serving 6 screenshots at native 1226×800 resolution when displayed at ~498×312 — not yet fixed, flagged for `frontend` (the mobile LCP element is the Hero's own text, not an image, so the fix isn't purely "compress the carousel," it needs a real look at render-blocking resources too). `Logo.tsx`'s two `<img>` tags gained explicit `width={543} height={620}` (the SVGs' real viewBox) to satisfy Lighthouse's unsized-images check — a one-line fix, done.
- **Structured data (JSON-LD, 2026-09-10)**: added, no longer deferred — `layout.tsx` carries a sitewide `Organization` + `SoftwareApplication` `@graph` (pricing represented as an honest `AggregateOffer` spanning the real published per-unit rates, since the pricing model is graduated-per-unit, not a single flat price schema.org has a clean way to express), and `/preguntas-frecuentes` additionally carries its own `FAQPage` schema sourced from `src/lib/faqs.ts`.

## Maintenance mode and error pages

Same two mechanisms as Condo-Admin-Tool (2026-09-10) — see that repo's own CLAUDE.md for the full rationale, ported here identically:

## Conventions

- **UI text** is Spanish; **code comments** are English — same split as the main app.
- Tailwind CSS v4 utility classes only — this project has no legacy plain-CSS "hub classes" to preserve (unlike the main app's deliberate `.panel`/`.status`/etc. exception), so every element here should be 100% Tailwind.
- Color tokens live in `globals.css`'s `@theme inline` block (`--color-primary`, `--color-text-muted`, etc.) — reuse them, don't hardcode hex values.
- Only two real breakpoints: `mobile` (720px), `tablet` (1000px) — no `lg`/`xl`/`2xl`.
- No manual dark-mode toggle (v1) — dark tokens live under `@media (prefers-color-scheme: dark)`, and Tailwind's default `dark:` variant already follows that.
- `clsx` for conditional classNames; never combine an always-applied Tailwind utility with a conditionally-appended one for the same CSS property (see `PricingCard.tsx` for the correct mutually-exclusive-ternary pattern) — same gotcha the main app has documented.
- New interactive logic goes in its own hook under `src/components/landing/hooks/useX.ts`, not inlined into a section component.
- A single fallback/constant value needed by more than one file (a URL, a shared copy string) belongs in its own module (`src/lib/siteUrl.ts` is the precedent) — don't copy-paste a literal into a second file, see the SEO section above for what that already cost once.
- Path alias `@/*` → `src/*`.
- 5 subagents live under `.claude/agents/` (`frontend`, `backend`, `security`, `qa`, `seo`), ported from the main app and rescoped to what this single-page site actually needs.
- **Document as you go**: update this file's relevant section in the same session you change how a section, the lead flow, or a pattern works.

## Product screenshots (`public/screenshots/`)

Recaptured with `scripts/capture-screenshots.mjs`, not by hand. They had been taken ad hoc, which is how the set shipping until 2026-09-11 went stale: captured 2026-09-08 from a condominium showing **₡0 collected and ₡396 000 overdue** — the marketing image of the payments feature advertised nothing collected — and carrying the Title Case bug that was fixed in the app the same day.

```bash
npm install --no-save playwright     # node_modules only; never a dependency of this project
# with Condo-Admin-Tool's dev server running:
CAPTURE_EMAIL=... CAPTURE_PASSWORD=... node scripts/capture-screenshots.mjs
```

The account must administer a condominium that **looks like a well-run building** — real collection for the current month, a small but non-zero morosidad, some announcements, reservations and vendors — with `tutorialsEnabled`/`pwaTutorialEnabled` off so no tour overlay lands in the frame. An empty condominium is a worse advertisement than no screenshot.

Two traps the script now documents in place, both hit while writing it:

- **Wait on the login *response*, not on a heading.** Waiting for `heading level 1` passes instantly, because the login screen has an `h1` too — a wait satisfied by the state you are trying to leave proves nothing, and everything after it runs against the wrong page.
- **Playwright matches an accessible name by substring by default.** `getByRole("button", { name: "Cerrar" })` also matches **"Cerrar sesión"**, so the overlay-dismissing helper logged itself out after the first screenshot and captured the login screen for every page after. Anything dismissing an overlay by name needs `exact: true`.

Captured at `deviceScaleFactor: 2` (2560×1600 and 780×1688) so they stay sharp on a retina screen now that the hero shows them large — ~2.4 MB of PNG in the repo, which **never reaches a visitor**: `DeviceFrames.tsx` renders every screenshot through `next/image`, so they are served as WebP/AVIF resized per viewport and lazy-loaded below the fold. Measured on the production build: **71 KB on first paint, 112 KB after scrolling the whole page**, against ~2.4 MB if they shipped raw (and ~800 KB even for the older 1× set, which loaded eagerly). `DeviceFrames` is the only place in the site that renders a screenshot, which is why that one file covers all of them.

`sizes` is load-bearing on both frames — without it `next/image` assumes `100vw` and ships a needlessly large variant, undoing the gain. The hero's frames pass `priority` so they are not lazy-loaded, since they are the LCP element.

**Verifying lazy-loading needs a real browser.** In an automated/offscreen pane, Chrome does not fire native lazy-loading on scroll, so every below-the-fold screenshot reads as blank and looks like a bug that isn't there. Confirmed with a headless Chromium walking the page: 11 of 18 images load, and **zero are in the viewport and blank** (the remaining 7 sit off-screen inside the horizontal carousel and load when it is swiped).
